Spring Security in SecurePay

Spring Security in SecurePay

The core ideas of Spring Security, then what Spring Boot sets up for you. Each one is shown with the lines from your own project that use it.

Spring Security

1

The filter chain

Security runs before your controller, as servlet filters. FilterChainProxy holds your SecurityFilterChain beans and uses the first one whose matcher fits the request. Nothing in a chain runs for a request it doesn't match.

payment-authorization-server/…/Config/SecurityConfig.java

@Bean @Order(1)   // only the OAuth2 endpoints: /oauth2/authorize, /oauth2/token, /oauth2/jwks…
SecurityFilterChain authorizationServerSecurityFilterChain(HttpSecurity http) {
  http.securityMatcher(authorizationServerConfigurer.getEndpointsMatcher()) …

@Bean @Order(2)   // no securityMatcher: everything else, like /login and /register
SecurityFilterChain defaultSecurityFilterChain(HttpSecurity http, …) { … }

So POST /oauth2/token runs chain 1, and POST /login falls through to chain 2. Swap the @Order values and chain 2 would catch everything first.

2

Authentication: who are you

One filter turns credentials into an Authentication object, with help from an AuthenticationProvider. SecurePay uses two different kinds.

auth-server: form login (password)

.formLogin(form -> form.loginPage("/login").failureHandler(failureHandler))
// UsernamePasswordAuthenticationFilter → DaoAuthenticationProvider
//   → CustomUserDetailsService (MySQL authdb) → BCrypt check

service-a, service-b, notification: bearer token (JWT)

.oauth2ResourceServer(oauth2 -> oauth2.jwt(Customizer.withDefaults()))
// BearerTokenAuthenticationFilter → JwtAuthenticationProvider
//   → JwtDecoder: RS256 signature, iss, exp → JwtAuthenticationToken

So A and B never see a password. They only verify a signature with :9000's public key.

3

SecurityContext: where the user lives

The result goes into SecurityContextHolder, which is thread-local and lasts for one request. With STATELESS sessions it is rebuilt from the token on every request.

payment-service-b/…/Service/PaymentServiceImpl.java

private String currentUser() {
  return SecurityContextHolder.getContext().getAuthentication().getName();   // JWT "sub"
}
paymentEntity.setOwner(currentUser());

payment-service-b/…/Notification/PaymentCreatedEvent.java

public record PaymentCreatedEvent(String paymentId, String owner, BigDecimal amount)

So the event carries owner explicitly because the @Async listener runs on another thread, where the context is empty.

4

Authorization: what may you do

AuthorizationFilter checks your URL rules against the user's authorities. For a JWT, each scope becomes an authority with a SCOPE_ prefix.

payment-service-a/…/Security/SecurityConfig.java (same rules in B)

.requestMatchers(HttpMethod.POST, "/payments/**").hasAuthority("SCOPE_payment.write")
.requestMatchers(HttpMethod.GET,  "/payments/**").hasAuthority("SCOPE_payment.read")
.anyRequest().authenticated()

URL rules can't know who owns a row, so that check lives in the query:

paymentRepository.findById(paymentId)
    .filter(x -> currentUser().equals(x.getOwner()))   // not yours → 404

So the filter answers "may you read payments?", and your service answers "is this payment yours?". You need both.

5

401 or 403

ExceptionTranslationFilter catches what fails after it and picks a response. Unknown or bad credentials go to the entry point (401). Known user, missing permission goes to the access-denied handler (403). A token that fails to decode never gets that far: BearerTokenAuthenticationFilter sends the 401 itself.

expired token          → 401  WWW-Authenticate: Bearer error="invalid_token"
token with only read   → 403  WWW-Authenticate: Bearer error="insufficient_scope"
HTML request, no login → 302 /login   (auth-server, LoginUrlAuthenticationEntryPoint)

So the same failure looks different per client. Your auth server sends browsers to /login and everyone else gets a 401.

Spring Boot security

6

The starter gives you a default chain

Add spring-boot-starter-security and Boot registers DelegatingFilterProxy plus a default chain: every request needs a login, with form login and HTTP Basic. The moment you declare your own SecurityFilterChain bean, Boot's default backs off.

So every SecurityConfig in SecurePay replaces Boot's default rather than adding to it. A path you forget falls to your anyRequest() line.

7

Properties become security beans

Most of your OAuth2 setup is properties. Boot reads them and builds the beans.

payment-service-a/…/application.properties

spring.security.oauth2.resourceserver.jwt.issuer-uri=http://localhost:9000
# → a JwtDecoder bean. On the first token it reads /.well-known/openid-configuration,
#   fetches /oauth2/jwks, caches the keys, and also checks that "iss" matches

payment-service-b/…/application.properties

spring.security.oauth2.client.registration.notification.authorization-grant-type=client_credentials
spring.security.oauth2.client.registration.notification.scope=notification.send
# → ClientRegistrationRepository + OAuth2AuthorizedClientService,
#   which NotificationClientConfig wires into the WebClient

So the JWT check in A, B and Notification is one property each. B calling Notification as itself is a registration plus one filter function.

8

Passing identity between services

There are two ways to call the next service, and SecurePay uses both.

A → B    ServletBearerExchangeFilterFunction                    relays the user's token (sub = nithin)
B → 8082 ServletOAuth2AuthorizedClientExchangeFilterFunction    B's own token (sub = payment-service-b)

So B checks the user's scopes again rather than trusting A. Notification doesn't care which user it is; it only needs notification.send.

Found in your code

In registeredClientRepository, payment-client calls .tokenSettings(...) twice. The second call replaces the first, so reuseRefreshTokens(false) is lost and refresh tokens are reused (the default). The 1-hour refresh lifetime you set happens to equal the default, so that part didn't change. Put all four settings in one TokenSettings.builder().
