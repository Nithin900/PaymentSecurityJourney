Build it: the developer view

Starting a feature = asking questions. The questions are general (same in every project). The answers are SecurePay's. Your answers become your list of classes.

You writea class You configureyml, @Bean or DSL line Spring / no code
Beans & dependency injectionBean lifecycleAOP@TransactionalSpring Boot: starters & configurationREST APIError handlingDatabaseSecurityCalling another serviceEventsObservability

Any new feature: ask these first

Go through the list, write one-line answers, skip what doesn't apply. Each line opens the card with the detailed questions.

  1. Security — Who calls it and what are they allowed to do? Whose data is it?
  2. REST API — Which URL, method, request, response and status codes?
  3. Errors — What can go wrong and what does the caller see?
  4. Database — What is stored or changed? Which queries?
  5. Transactions — What must succeed or fail together?
  6. Other services — Which services do I call? What if they are down?
  7. Events — Who needs to know afterwards?
  8. Observability — How will I see it working (or failing) in production?
  9. Beans & config — Which classes, which settings, what changes per environment?

Then write in this order: DTOs → entity + migration → repository → service (+ transaction, rules) → controller → error mapping → security rule → events → tests.

Beans & dependency injection

Spring Core
  1. 1Which classes hold business logic or talk to other systems?
    SecurePayPayment rules, refunds, the Service B client, the event publisher.
    You write@Service / @Component classes with constructor injection (final fields, one constructor, no @Autowired needed).
  2. 2Which objects come from a library, so I can't put an annotation on them?
    SecurePayClock (for testable time), a configured WebClient.
    You write@Configuration class (e.g. AppConfig) with @Bean methods.
  3. 3Is there more than one implementation of the same interface?
    SecurePayFraudCheck: real rules in prod, a no-op locally.
    You configure@Profile("local") or @ConditionalOnProperty to choose one; @Primary / @Qualifier if both must exist.
  4. 4Does any bean keep data that changes per request or per user?
    SecurePayNo. Request data travels as method parameters; beans are singletons shared by all threads.
    Spring / no codeKeep beans stateless (no mutable fields). Only if really needed: request scope or ObjectProvider.
  5. 5Do two services need each other?
    SecurePayPaymentService ↔ RefundService would be circular.
    You writeMove the shared logic into a third class, or publish an event. Don't hide it with @Lazy.
  6. 6Can I unit-test the class without starting Spring?
    SecurePayYes, because of constructor injection.
    You writenew PaymentService(mockRepo, Clock.fixed(...)) in a plain JUnit + Mockito test.

@Transactional

Spring Core
  1. 1Which database writes must all succeed or all fail?
    SecurePayRefund: insert the Refund row + change Payment status.
    You write@Transactional on the public service method (RefundService.refund), not on the controller or repository.
  2. 2Is this method only reading?
    SecurePayGET payment, list payments.
    You configure@Transactional(readOnly = true) (Hibernate skips dirty checking; lazy fields load inside).
  3. 3Which exceptions should roll back?
    SecurePayBusiness failures like "refund exceeds amount".
    You writeMake them RuntimeExceptions, or rollbackFor = Exception.class — checked exceptions commit by default.
  4. 4Must something be saved even if the main work rolls back?
    SecurePayAudit row "refund attempt failed".
    You writeSeparate bean AuditService with @Transactional(propagation = REQUIRES_NEW).
  5. 5Does the transaction call a slow external system?
    SecurePayCalling Service B / a gateway would hold the DB connection.
    You writeCall it outside the transaction, or split: tx1 save PENDING → call → tx2 update.
  6. 6Can two requests change the same row at once?
    SecurePayTwo refunds of the same payment.
    You write@Version on the entity (optimistic lock) → 409 on conflict. See JPA.
  7. 7Does something happen only after the commit?
    SecurePayPublish PaymentRefunded to Kafka.
    You write@TransactionalEventListener(phase = AFTER_COMMIT), or an outbox table for guaranteed delivery.

You write

  • service/RefundService (@Transactional)
  • service/AuditService (REQUIRES_NEW)
  • exception classes extending RuntimeException

Spring gives you

  • TransactionInterceptor (proxy)
  • JpaTransactionManager (auto-configured)
  • TransactionSynchronizationManager (connection bound to the thread)

Error handling

Spring MVC
  1. 1What business failures can happen?
    SecurePayPayment not found, already refunded, refund too large.
    You writeOwn exceptions: PaymentNotFoundException, RefundNotAllowedException (extend RuntimeException).
  2. 2Which status code for each?
    SecurePay404, 409, 422.
    You writeGlobalErrorHandler: @RestControllerAdvice with @ExceptionHandler methods returning ProblemDetail.
  3. 3What JSON shape do clients get?
    SecurePayRFC 9457 ProblemDetail for everything.
    You configureExtend ResponseEntityExceptionHandler (or spring.mvc.problemdetails.enabled=true) so Spring's own errors use the same shape.
  4. 4What about invalid input?
    SecurePay@Valid fails → 400 with field errors.
    You writeOverride handleMethodArgumentNotValid to add the field list.
  5. 5What about unexpected errors?
    SecurePay500, no stack trace to the client, full log with traceId.

  6. 6What about 401/403?
    SecurePayURL rules fail in the security filter chain, before the controller.
    You configureNot the advice — Security's AuthenticationEntryPoint / AccessDeniedHandler. Keep /error permitted.
