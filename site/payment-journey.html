2 · Big picture

Who does what 
Postman ──login + consent──► Auth Server :9000 ──JWT (RS256, 5 min)──► Postman
Postman ──Authorization: Bearer JWT──► Service A :8080 ──same JWT──► Service B :8081 ──► H2 file DB
ServiceJobKnows about
payment-authorization-server :9000Logs users in, asks for consent, issues signed JWTs, publishes its public keysUsers (nithin, alice), the client payment-client, the signing key
payment-service-a :8080Gateway. Checks the token and scope, forwards the call to B with the same token, maps B's errorsNo database. No payment logic
payment-service-b :8081Stores payments in H2, checks the token itself, enforces ownershipThe PAYMENTS table

Three ideas that explain the whole design

  • Only the auth server creates tokens. A and B only verify them, using the public key. They never see a password.
  • Scope decides whether you may call an endpoint (SCOPE_payment.read to GET, SCOPE_payment.write to POST). Ownership decides which payments you may see (the token's sub must equal the payment's owner).
  • B never trusts A. Anyone can call B directly on 8081, so B validates the JWT itself and reads the user from that JWT, not from anything A sends.

3 · How a token is born (Authorization Server)

The login → consent → code → token flow, and the code behind each step 
1. Client opens   GET /oauth2/authorize?response_type=code&client_id=payment-client&scope=payment.read payment.write&redirect_uri=...
2. Not logged in  → 302 /login           (LoginUrlAuthenticationEntryPoint)
3. User posts     POST /login  username + password + _csrf   → session cookie
4. Back to        GET /oauth2/authorize  → consent page (first time) or a redirect with ?code=... (consent remembered)
5. User approves  POST /oauth2/authorize  client_id + state + scope checkboxes → 302 redirect_uri?code=XYZ
6. Client swaps   POST /oauth2/token  Basic payment-client:secret + grant_type=authorization_code + code
7. Server answers {"access_token":"eyJ...", "token_type":"Bearer", ...}   (a signed JWT)

What each bean in SecurityConfig (auth server) does, and why it exists

Bean / methodWhat it doesWhy it's written this way

Browsers without a login are sent to /loginThe OAuth protocol is implemented by filters, not controllers. securityMatcher(getEndpointsMatcher()) makes this chain apply only to those URLs
defaultSecurityFilterChain @Order 2Everything else: login page via formLogin, all other pages need a loginCatches what chain 1 didn't claim. Provides the form that step 3 posts to

What is inside the token

header : {"alg":"RS256","kid":"…"}
claims : {"iss":"http://localhost:9000","sub":"nithin",
          "scope":["payment.read","payment.write"],"iat":…,"exp": iat + 300, …}
signature = RSA-sign(header.claims, private key)      ← only the auth server has the private key

4 · Service A (the gateway)

Every piece of A and why it exists
Class / methodWhat it doesWhy it's written this way
SecurityConfig.securityFilterChainOpen: /actuator/health, /error. POST /payments/** needs SCOPE_payment.write, GET /payments/** needs SCOPE_payment.read. Everything else needs a token. Stateless, CSRF offRules are checked top to bottom, first match wins, so the specific rules sit before anyRequest().authenticated(). SCOPE_ is the prefix Spring adds to each scope. No session or cookie carries identity, so CSRF protection has nothing to protect
.oauth2ResourceServer(o -> o.jwt(...))Installs the JWT filter and builds a decoder from spring.security.oauth2.resourceserver.jwt.issuer-uriOne line turns A into a resource server: it fetches the JWKS once, caches it, and checks signature, exp and iss on every request
PaymentControllerPOST /payments, GET /payments/{id}, GET /payments. Each just calls PaymentServiceControllers stay thin. A has no @Valid: validation is B's job, and A passes B's 400 through
PaymentServiceImplCalls B with webClient and .block(). In getPayment, a 404 from B is caught and rethrown as B's PaymentNotFoundException.block() keeps the call on the request thread, which is what lets the token relay find the caller's JWT. Translating the 404 gives A one clean exception type to map
WebClientConfig.webClientReactor Netty client with 2 s connect and 3 s response timeouts, base URL http://localhost:8081, and ServletBearerExchangeFilterFunctionWithout the connector the timeouts are silently ignored and a hung B would hold A's threads. The filter copies the caller's bearer token onto the outgoing call, so B sees the real user
GlobalExceptionHandlerTurns exceptions into JSON: 404 for not-found, 401/403 from B, B's own status for anything else, 503 when B is unreachable, 400 for bad JSON, 404 for unknown routes, 500 as the last resortSpring picks the most specific handler. The not-found handler was once commented out, so B's 404 fell into the catch-all and came out as a 500

Gotcha in WebClientConfig

The method takes WebClient.Builder builder but returns builder() (a static import), which creates a new builder. The injected one is never used. It works, but to use Spring Boot's builder (which carries tracing instrumentation) write builder.baseUrl(...)… without parentheses and drop the static import.

6 · Data at each hop

What the data looks like as it travels (POST /payments)
HopWhat travels
Postman → APOST http://localhost:8080/payments
Authorization: Bearer eyJ… · Content-Type: application/json
body {"paymentId":"OWN-1","accountNumber":"acc-123","amount":25.00}
Inside AJackson builds PaymentRequest(paymentId, accountNumber, amount:BigDecimal). The verified token becomes a JwtAuthenticationToken in SecurityContextHolder (authorities SCOPE_payment.read, SCOPE_payment.write)
A → BPOST http://localhost:8081/payments with the same Authorization: Bearer header and the same JSON body, re-serialized from PaymentRequest
Inside BToken verified again → validated request → Payment(id, accountNumber, amount, owner="nithin")
B → H2insert into payments (payment_id, account_number, amount, owner) values ('OWN-1','acc-123',25.00,'nithin')
B → A → Postman200 {"paymentId":"OWN-1","status":"SUCCESS","message":"Payment created Successfully"}. A reads it into PaymentResponse and returns it unchanged

OWN-1      | acc-123        | 25.00  | nithin        ← nithin's token: 200   ·   alice's token: 404

7 · Who returns which error

Status codes, who produces them, and why
StatusWhenProduced by
401No token, garbage token, expired tokenA's (or B's) JWT filter → BearerTokenAuthenticationEntryPoint; the controller is never reached
403Valid token but the wrong scope (e.g. read-only token on POST)AuthorizationFilter → BearerTokenAccessDeniedHandler in A
404Payment missing or owned by someone elseB: PaymentNotFoundException → 404. A catches B's 404 and returns its own 404. Unknown route: A/B NoResourceFoundException
409Duplicate payment idB (DuplicatePaymentException or a database key violation); A passes it through
400Validation failure (amount ≤ 0), malformed JSONB validates and A passes it through; A itself rejects broken JSON
503B down, connection refused, connect or response timeoutA: WebClientRequestException → bDown
500Anything unexpectedThe catch-all handler. Seeing this for a not-found means a handler is missing

9 · Testing

Postman collections and how to run them
Collection (in postman/)Use
Payment-ServiceA-AutomatedMain suite. Logs in as nithin, alice and a read-only nithin by script, then tests A: 401/403, create/get/list, ownership (404), duplicate (409), validation (400), malformed body, unknown route. Optional folder for 503 (stop B first)
Payment-Ownership-AutomatedSame login automation, ownership tests straight against B
Payment-Microservice-OAuth2, PaymentMicroServiceManual walkthrough: browser for login and consent, copy the code, exchange it
  • Open the collection and press Run collection. Tokens last 5 minutes and die on a dev auth-server restart, so just re-run.
  • Consent is remembered until the auth server restarts. After the first approval the consent step shows skipped, which is expected.
  • Each run uses fresh payment ids, so repeated runs don't collide.

10 · Known limits

What this project does not do yet
  • Old rows have no owner. Payments saved before ownership existed have owner = NULL and are invisible. Delete payment-service-b/data/, or UPDATE PAYMENTS SET OWNER='nithin' WHERE OWNER IS NULL.
  • sub must be a person. A client-credentials token has sub = <client id>, so payments made that way belong to the client.
  • Learning-only security shortcuts: withDefaultPasswordEncoder(), in-memory users and clients, a fixed secret.
  • A depends on B's classes (it reuses PaymentNotFoundException), so A's build needs B's module.
  • Not built yet: client credentials for settlement-job, and distributed tracing.
